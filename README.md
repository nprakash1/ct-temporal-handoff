## How feature extraction connects to frozen-model training

**Notebook 04 supplies the image-feature cache consumed by notebooks 01 and 02.**
It is a preparation step, not a separate progression model or a required rerun.

```text
04: individual CT volumes → frozen CT-CLIP → one 512-D vector per scan
                                               |
             /content/drive/MyDrive/3dCT/ctclip_cache/img/
                                               |
                 + paired scan IDs + compatible direction labels
                                               |
                 01: frozen-feature temporal adapter / loss sweep
                 02: separate held-out wording training/evaluation sweep
```

- **04:** no progression labels or scan-pair comparison; no training. It writes
  normalized, half-precision 512-D tensors named by scan volume ID.
- **01/02:** read those tensors as the prior/current inputs and train the temporal
  adapter while CT-CLIP remains frozen. They separately encode text targets and
  prototypes. Notebook 02 is its own experiment, not just an evaluation command
  for the checkpoint produced by 01.
- **Order:** if compatible features are missing, run 04 first; otherwise start
  with 01 or 02 using the existing cache. Neither training notebook automatically
  runs 04. Supply their historical paired-report labels separately; 05 is not a
  prerequisite and its output is not directly interchangeable with those labels.
- **Compatibility:** check scan-ID coverage, backbone/checkpoint revision and
  preprocessing provenance. The extractor only skips existing filenames; it does
  not validate file integrity or feature provenance. Do not mix incompatible caches.
- **03 is different:** it builds/loads its own intermediate encoder-prefix cache.
  The final 512-D vectors from 04 cannot replace those prefixes.

This maps the code's producer/consumer relationship; it does not prove that every
feature used by the historical runs was generated by this exact extractor revision.

## What the label names mean — no project history required

MedGemma is used as a **report-text labeler**, not an image reviewer. It identifies
whether each finding worsened, stayed stable, or improved. These are **silver
labels**: automated judgments that have not been independently verified on the
CT images. A version number is an internal artifact identifier, not a MedGemma
model version or a guarantee of label quality.

| Descriptive name used in this guide | What it means | Used by | Legacy identifier in filenames |
|---|---|---|---|
| **Report-comparison labels for the frozen baseline** | MedGemma receives prior/current reports and is instructed to extract comparisons stated in the current report. Postprocessing gives these extracted comparisons precedence over structured presence changes. Training keeps entries marked `tier: explicit`; that flag is not independent clinical verification. | 01 and 02 | `v3` |
| **Filtered report-comparison labels with standardized training text** | The original labeler receives prior/current reports plus noisy structured presence transitions. It is instructed to distinguish explicit comparison language from static descriptions. The training loader keeps report-explicit, text-grounded directions. A separate script adds template sentences matching those existing labels for text alignment; it does not verify or relabel the scans. | 03 | `v6` plus `synthetic_direction` |
| **Current-report-only labeling** | MedGemma sees only the current report when judging explicit progression. Prior-report descriptions and structured transitions are withheld from the model at this step. Code applies structured new/resolved fallback afterward and records its source separately. This is intended to reduce confusing static descriptions with explicit change. | 05; not used for the historical results in 01–03 | `v7` |

**Why the distinction matters:** a finding being present in both reports does not
prove stability. “Pleural effusion is present” is a static description; “pleural
effusion has increased since the prior examination” is an explicit comparison.
Checking that a quote exists in a report verifies text grounding, not the clinical
truth of the label or whether it refers to the exact paired prior scan.

**Do not swap these datasets by renaming files.** The frozen-baseline loader uses
the `tier` field, while the later label formats use source/grounding fields such
as `label_source` and `report_grounded`. Notebook 03 also checks an exact input
hash. A new label set needs an explicitly adapted loader, audited splits and a
new experiment identity. Exact legacy filenames below are retained solely to
locate the artifacts used by the recorded runs.

### How can one report provide progression?

**This extracts progression already described by the radiologist; it does not
independently compare CT images or infer change by comparing two static reports.**
The following are illustrative examples, not patient text:

| Current-report statement | Report-extraction decision |
|---|---|
| “The right pleural effusion has increased compared with the previous examination.” | Worsened; retain the supporting report sentence. |
| “The pulmonary nodule is unchanged from the previous study.” | Stable; retain the supporting report sentence. |
| “The previously seen consolidation has resolved.” | Improved; retain the supporting report sentence. |
| “There is a right pleural effusion.” | No explicit comparison (`not_temporal`); this statement alone cannot establish progression. |

The prior report and structured presence transitions are deliberately hidden from
MedGemma at this extraction step. This reduces the opportunity to mistake changed
wording or omission for an explicit comparison. It does **not** eliminate labeling
errors or prove that the radiologist's reference examination is the paired scan.

### What happens when there is no usable explicit comparison?

The separate `combine`/`fallback` code uses the manifest's noisy predicted
presence/absence transitions when there is no accepted, text-grounded report
comparison (including when an extracted quote fails grounding checks):

| Structured transition | Fallback output | Interpretation |
|---|---|---|
| Absent before → present now | New / worsened | Inferred from presence predictions, not an explicit report comparison. |
| Present before → absent now | Resolved / improved | Inferred from presence predictions, not an explicit report comparison. |
| Present in both | Unknown / no comparison | **Not stable** merely because both scans have the finding. |
| Absent in both | Absent / unknown direction | Not a progression training target by itself. |

The two sources remain distinguishable in the output:

- Accepted report comparison: `label_source = report_explicit`,
  `report_grounded = true`, `temporal_sentence_source = real_report`.
- New/resolved presence fallback: `label_source = structured_presence`,
  `report_grounded = false`, `temporal_sentence_source = synthetic_presence`.
  Its template sentence is generated by code, **not a quote or independent evidence**.
- Present-both without an accepted comparison: `direction = unknown` and
  `label_source = unknown`. Rejected evidence/reasons are retained for inspection.

These are implemented provenance distinctions, not a validated hierarchy of
clinical accuracy. Do not silently mix fallback and report-explicit labels in
training/evaluation. Define eligibility explicitly and report counts by source.

### Unresolved: does the report compare against the exact paired prior CT?

**The current labeling code does not verify this.** Verbatim quote checks establish
that text came from the current report; they do not establish which previous
examination it references. Pairing consecutive dated scans alone does not solve it.

Before claiming a verified longitudinal benchmark, the next owner should:

1. Match report comparison dates or examination identifiers, where available,
   against the selected prior scan, respecting authorized data access.
2. Flag mismatches and ambiguous references; exclude or review them under a
   documented policy rather than assuming correspondence.
3. Record comparison-match status separately from `report_grounded` and label source.
4. Build an image-reviewed evaluation subset and audit both scans' correspondence.

These are **recommended follow-up tasks, not completed checks**. Notebook 05 is
an optional future-labeling workflow and does not retroactively validate the
historical results in notebooks 01–03. All report-derived labels remain silver.
